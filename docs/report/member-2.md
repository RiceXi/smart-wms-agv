## 2. 需求分析

公共需求（`docs/requirement.md` + `docs/data-schema.md` + `docs/acceptance.md`）可以拆成
五条互相依赖的主线，我按这五条主线确定了自己的实现边界：

1. **主数据与业务事实**：SKU、库位、库存（含流水）、出库订单、拣选任务。
   状态机由公共契约钉死（任务 `pending→assigned→running→completed`，订单
   `draft→allocated→released→completed/cancelled/failed`），不能自由发挥。
2. **调度内核**：把订单拆成任务、指派给 AGV、规划路径、避免冲突、处理死锁。
   这是整个系统真正的难点，也是验收用例 AC5–AC13 的重心。
3. **仿真运行时**：离散 tick 推进，覆盖运动、装卸、充电、故障、离线、封路、急单。
   要求时间统一 UTC 存储、仿真 tick 用整数、固定场景用明确 seed。
4. **可观测性**：实时地图、任务路径、轨迹、告警、冲突与死锁事件、吞吐与利用率统计。
   要求统计口径明确，前端不得伪造任何状态或指标。
5. **工程要求**：健康检查、结构化日志、可复现的本地启动、跨服务写操作带幂等键、
   算法可脱离 UI 测试、持久化不丢数据。

三条我主动划定的边界：

- **不入库任何演示数据**。8 个固定场景全部由 Python 代码定义，`python -m wms export-fixtures`
  导出成 JSON，保证"场景定义"和"fixture"不会漂移（有自动化测试守着这条）。
- **不伪造成功**。30 台 AGV 场景有 7 个任务失败，我选择如实写进报告，而不是调参调到全绿。
- **不做课程推荐技术栈**。Spring/Kafka/Redis/Eureka 留给整合版，本个人版用标准库自研，
  并在设计文档里给出两者的映射关系。

## 3. 开发计划

我把开发分成 6 个阶段，每阶段都有可观察的完成条件，避免"看起来写了很多但跑不起来"：

| 阶段 | 内容 | 完成条件 |
| --- | --- | --- |
| ① 契约与骨架 | 读完全部公共文档；冻结 API 契约；建目录 | `docs/api-contract.md` 定稿，前后端都以此为准 |
| ② 数据与持久化 | SQLite schema、领域模型、业务服务层 | 订单 → 任务的状态机能跑通 |
| ③ 调度内核 | 时空 A*、预约表、指派评分、等待图死锁检测 | 四个模块都是纯函数/纯内存对象，不依赖 DB 与 UI |
| ④ 仿真运行时 | tick 主循环、装卸、充电、故障、封路、急单 | 单 AGV 场景能闭环完成一个订单 |
| ⑤ 接口与前端 | REST、SSE、Canvas 控制台 | 浏览器打开页面能实时看到 10 台车跑起来 |
| ⑥ 验收与交付 | 91 个用例、8 个场景回归、AC1–AC20、文档与报告 | 逐条有命令级证据 |

阶段②→③之间有一次调整：原计划把地图版本管理放在②，实践中发现"封路必须生成新版本"
和"重启后要恢复版本"是同一件事，于是把 `MapStore.restore_current()` 提前到②做，
③ 就不用再关心持久化细节。

## 4. 技术选型与架构设计

**选型：Python 3 标准库 + SQLite + 原生 JS/Canvas，零第三方依赖。**

理由是验收 AC1 要求"从干净环境按说明启动"。如果选 Spring Boot + Kafka + Redis + Eureka，
需要 JDK、Maven、Kafka、Redis 四套环境，任何一个装不上或版本不对都会卡住验收；
而标准库方案在干净机器上 `python -m wms serve` 就能跑，前端也不需要 npm。
代价是不能多实例水平扩展——这一点我在设计文档第 10 节给出了与课程推荐技术栈的逐项映射，
由整合版承接。

架构分四层，边界是刻意划出来的：

```text
浏览器（Canvas + 原生 JS）
      │  REST + SSE
server.py / api.py        ← HTTP 层不含业务逻辑
      │
simulator.py  service.py  analytics.py
      │            │            │
pathfinding.py  scheduler.py  deadlock.py
      │            │
reservations.py         mapdata.py / mapgen.py
      │
   db.py（SQLite）
```

三条硬约束：

1. **业务事实只有一个写入口** `service.py`。仿真层不能直接改任务状态，只能调用状态机方法，
   所以"哪些流转合法"只在一个文件里定义，可测、可审计。
2. **仿真时间与真实时间彻底分离**。1 tick = 1 秒仿真时间，真实时间只决定"多久推进一个 tick"。
   于是回放结果与机器性能无关，AC13 的"同 seed 结果一致"才立得住。
3. **地图不可原地修改**。封路生成新版本（`map-1` → `map-1-r1` → …），旧版本留在库里，
   这样"封路前后的路径差异"可以事后对账。

调度内核的三个核心设计（详见 `implementations/member-2/docs/design.md`）：

- **时空 A***：节点是 `(格点, tick)`，扩展时同时检查顶点预约、有向边预约与**反向边预约**
  （反向边检查就是 AC7"相向穿边"的拦截点）。为避免无解空间爆搜，加了
  `static_reachable` 静态预检（只避开静止车辆）和展开数上限两道保险。
- **预约表**：批量申请必须整体成功；抢占要求优先级**严格更高**且只能抢"未来 tick"的预约
  （已到达的是历史事实）；同优先级冲突走等待或绕行。另有静态占位表表达"这辆车一直停在这里"。
- **死锁恢复**：等待图用带颜色标记的确定性 DFS 找环；判定死锁要求"连续阻塞 ≥ 2 tick"，
  过滤瞬时等待；选牺牲者时先看能不能回退，回退格用 Tarjan 求出的**割点集合**排除——
  回退车停在割点上会把唯一通道堵死，反而恢复不了。

## 5. 数据模型与核心流程

数据模型（SQLite，共 18 张表）遵循公共契约第 2–9 节。几个自己做的判断：

- **货架格不可通行 ⇒ AGV 不能开到货架前**。任务模型因此变成：AGV 开到同区域的拣选点，
  在拣选点完成取货确认，再扣减对应货架格上的库存。同一区域有多个拣选点时，
  选当前在办任务数最少的一个，避免所有车挤到同一工位排队。
- **订单与任务是一对多**：一行明细一个任务，释放订单即生成任务，重复释放幂等。
- **库存预占用 `reserved_qty` 单独记账**，不直接扣 `qty`；真正的扣减发生在任务完成时，
  按 `order_allocations` 精确扣减，因此一个明细跨批次时也能算清。
- **事件双写**：`events` 表是全局事实流（供 SSE 与统计对账），`task_events` 表是任务生命周期
  （供任务时间线）。两者分开，是因为"按 AGV 过滤事件"和"按任务查时间线"是两个访问模式。

核心流程（订单 → 完成）：

```text
POST /orders            → draft，校验明细
POST /orders/{id}/release
      ├─ 校验状态（draft 才允许；released/completed 幂等返回）
      ├─ 按批次规则分配库存 → reserved_qty + N，写 order_allocations
      ├─ 订单 → allocated
      ├─ 按明细生成任务 → 订单 → released
tick 循环
      ├─ 任务队列按 priority DESC, created_at ASC 排序
      ├─ 打分选 AGV：cost = W_DISTANCE*距离 + W_LOAD*负载 − W_PRIORITY*优先级 + W_BATTERY*低电惩罚
      ├─ 时空 A* 规划 → 批量预约（原子）
      ├─ 移动 / 取货确认(2 tick) / 放货确认(2 tick) / 充电
      ├─ 等待图 → 死锁检测 → 选牺牲者 → 回退 → 重规划
      └─ 任务完成 → 按分配记录扣减库存 → 订单 → completed
```

## 6. 关键提示词与迭代过程

完整的提示词与迭代记录见 `implementations/member-2/ai-notes.md`。这里挑最能体现方法的 5 条：

1. **"先读完全部公共文档，再列出实现计划与需要我自己决策的点"** —— 我特意要求它把
   需要人拍板的问题（技术选型、哪些字段可以扩展）单独列出来，而不是自己悄悄决定。
   这一步直接决定了"只用标准库"这个后来被证明正确的选择。
2. **"先冻结接口契约，再让前后端分别实现"** —— 前端子 Agent 拿到的是一份字段名、
   枚举值、SSE 格式全部写死的契约文档。两边并行开工没有产生结构性冲突，
   剩下的全是契约没写到的细节，逐条补齐即可。
3. **"把调度算法写成不依赖 UI 和数据库的纯模块"** —— 这条来自 AGENTS.md 的硬要求
   "路径、预约和死锁算法必须可在无 UI 条件下测试"。实践里它救了我很多次：
   抢占语义错误、同优先级误抢占、死锁误判、割点回退这四个真实缺陷，
   都是先被纯单元测试逼出来的，而不是靠盯着页面看出来的。
4. **"先写测试再改实现；测试失败时先判断是测试写错还是实现有 bug"** —— 这条看起来像废话，
   但本轮至少有 4 次是我的测试写错了（tick 用错、用了不同 tick 导致预约不冲突、
   把 UUID 当成可比较的 id、把"急单晚于普通任务指派"当成 bug）。如果不强制自己先质疑测试，
   很容易为了让测试变绿而改坏实现。
5. **"为每个场景补一个定时事件机制，让封路场景真的会封路"** —— 我在跑场景回归时发现
   `roadblock` 场景的期望是 `replans: 1`，但实际 `map.roadblock.added` 事件数为 0：
   场景名字叫封路，实际上没有任何封路动作，**属于假覆盖**。这直接对应 AC20 的
   "不得把未运行功能标记为通过"。

## 7. AI 生成效果分析

**整体判断：AI 在"有明确规格的编码"上表现优秀，在"需要理解系统状态的地方"上会犯系统性错误。**

表现好的部分：

- **结构化代码的产出速度**。19 个后端功能模块、91 个测试用例、前端 2351 行，
  从零到可运行版本大约用了三轮迭代。模块边界清晰、注释密度合理、
  中文错误信息到位，这些都符合仓库的文档风格要求。
- **纯算法模块的初版质量高**。时空 A*、Tarjan 割点、等待图 DFS 三处初版几乎没有 bug，
  连"确定性排序"这种容易漏的细节都写进去了。
- **能自己发现自己的不一致**。给它一个明确任务时，它会先复述约束再动手；
  遇到契约空白点会主动列出来问，而不是自己编一个。

表现差的部分（**几乎全部集中在"跨模块的状态一致性"上**）：

- **改了一处忘了另一处**。典型是 `assign_task`：先用 SQL 把 `status` 改成 `assigned`，
  再调用统一的状态机方法，于是状态机看到 `from == to` 直接返回，`task.assigned` 事件被吞掉。
  这类 bug 单看任何一处代码都正确，只有把"事件流"和"状态机"放在一起看才会暴露。
- **对"已有对象的数据形状"记忆不准**。`active_roadblocks()` 返回 dict，AI 按对象写了
  `c.cell_id`，运行时直接 `AttributeError`。类似的还有 fixture 解析丢字段、
  `_allocate` 多返回值下标错位。
- **对"异常路径"考虑不足**。库存分配失败时，本行已经预占的库存没有回滚；
  重规划失败时保留了旧计划；重启时用基础地图重建，丢掉了已持久化的地图版本。
  这三条都属于"主干路径很happy，但失败/重启路径没写完"。

数据支撑：AI 首版代码约 5400 行，最终交付 5401 行（`wms/` 19 个功能模块），
另有前端 2351 行、测试 1123 行。**后端行数几乎没变**，
但其中约 700 行被我修改或重写。换句话说，AI 负责了约 **87% 的代码行**，
而剩下的 13% 恰好是全部的"逻辑正确性"所在。这是我这次最诚实的结论：
AI 显著提升了产出速度，但没有提升"发现系统性问题"的能力，这部分必须靠人主动设计验证方案。

## 8. AI 错误、幻觉与人工修改

完整清单见 `implementations/member-2/ai-notes.md`（21 条业务缺陷 + 9 条接口不一致 +
5 条场景/工具链问题）。这里列最有代表性的 9 条：

| 位置 | AI 的错误 | 为什么是错的 | 我的修改与验证 |
| --- | --- | --- | --- |
| `service._allocate` | 库存不足时抛 `InsufficientInventoryError`，但不回滚本行已预占的量 | "失败不留下部分扣减"是业务底线；订单释放失败却把库存吃掉是数据损坏 | 分配失败时先回滚本行预占再抛异常 → `test_release_without_stock_raises_and_keeps_state` |
| `service.assign_task` | 先改 `status` 再调状态机 | 状态机看到 `from == to` 提前 return，`task.assigned` 事件被吞，事件流缺一类事件 | 去掉 SQL 里对 `status` 的赋值，交给状态机 → 场景回归里 `task.assigned` 计数恢复正确 |
| `reservations.acquire` | 抢占时用 `keep_from_tick=current_tick+1` 释放受害者预约 | 语义正好相反：保留了冲突 tick 的预约，抢占永远失败；且同优先级也允许抢占，违反 AC6 | 新增 `release_from_tick` 参数（释放"从冲突 tick 起"的未来预约），并要求优先级严格更高 → 两个抢占/冲突用例 |
| `pathfinding.plan_path` | 起点不可通行直接返回 `None` | 施工封路正好落在车辆脚下时，车辆会被永久困住——这是真实世界最常见的封路情形 | 放宽起点检查（邻居仍按可通行过滤），车辆能驶离但不会重新进入 → `RoadblockTests` |
| `app._bootstrap` | 重启时用基础地图重建 `MapStore` | 重启后地图版本退回 `map-1`，封路记录丢失，车辆会走回已封闭的巷道，AC16 不成立 | 按库中记录的 `map_id` 重建基础地图 + `restore_current()` → `test_map_version_restored` |
| `simulator._replan` | 重规划失败时保留旧计划 | 车辆会沿旧计划走进已封路格点 | 失败时清空 `agv.plan` 并进入冷却重试 → `test_roadblock_triggers_replan_and_is_respected` |
| `simulator._replan` | 入口处 `if not agv.active_task_id: return`，把"没有任务的车辆"整个排除在重规划之外 | 空闲返程中的车会沿旧计划开进已封路的格点——AC10 的封路格里出现了车辆轨迹 | 新增 `_replan_idle_after_map_change`，仅在"地图版本变化"路径上对空闲车重规划 → `test_idle_returning_agv_also_replans` |
| `simulator` 冲突分支 | `stats["conflicts"]` 有两处只加计数、不发 `conflict.detected` 事件 | 统计口径与事件流对不上：`head-to-head` 场景统计报冲突 1 次，事件流里查不到 | 补发事件 → `test_conflict_counter_matches_conflict_events`（计数 1 = 事件 1，`peak-30` 计数 16 = 事件 16） |
| `server.WmsServer` | 只设 `allow_reuse_address = True`，绑定前不探测端口 | Windows 上 SO_REUSEADDR 允许两个服务"同时"绑定同一端口，浏览器请求被两个程序随机分流——用户打开 `127.0.0.1:8080` 看到的根本不是自己的页面 | 绑定前显式探测端口，冲突时抛 `PORT_IN_USE` 并提示换端口；默认端口改 8099 → `tests/test_api.py::PortConflictTests` |

**一条值得单独说的修复回退**（A19）：AI 给的第一版修法是把 `_replan` 改成"任何无任务车辆都重规划"。
单看 AC10 它是对的，但 8 个固定场景一回归，`peak-10` 从 10/10 完成退化成 9/10——多出来的重规划
把待命区车辆互相顶开。我把这版回退，收窄成"只在地图变化这条路径上重规划空闲车"，
两个场景同时满足。这件事让我改了验收习惯：**修完调度逻辑必须把所有固定场景重跑一遍，
单条用例通过不代表没有引入回归**。

**关于"幻觉"**：本轮没有出现虚构 API 或不存在的库调用（因为我从一开始就限定"只用标准库"，
依赖面小到可以逐个核对）。出现的是另一类问题：**假设了不存在的对象形状**和
**假设了不存在的前置条件**（例如假设 `active_roadblocks()` 返回对象、假设重启后
地图版本可以重新计算出来）。这说明对 AI 来说，"与外部世界交互的边界"是最需要人来兜底的地方。

## 11. 性能与限制

### 性能实测（AC19）

机器：Intel Core Ultra 7 155H / 31.5 GB RAM / Windows 11 家庭版 10.0.26200 / Python 3.14.3。

| 场景 | AGV | 任务 | 600 tick 耗时 | ms/tick | 指派延迟 avg/max（tick） | Python 堆峰值 |
| --- | --- | --- | --- | --- | --- | --- |
| single-agv | 1 | 1 | 0.36 s | 0.60 | 1.0 / 1 | 0.62 MB |
| peak-10 | 10 | 10 | 1.31 s | 2.18 | 1.0 / 1 | 1.79 MB |
| peak-30 | 30 | 30 | 5.52 s | 9.20 | 1.0 / 1 | 2.27 MB |

- 指派延迟定义：`task.assigned` 的 tick − `task.created` 的 tick。三个场景平均 1 tick。
- 前端帧率：8 倍速运行 `peak-10` 时页面 FPS 计数器稳定 **120 fps**（显示器刷新率上限），
  浏览器控制台 0 error / 0 warning。
- 测试时长：91 个用例 23–35 s（机器空闲时；同机并发跑 `serve` 或其它仿真任务时约 100 s，属 CPU 争用）。
- 场景回归总耗时：8 个场景合计约 5.5 s。

### 限制与风险

1. **单进程单库**：同一数据目录同时跑 `serve` 与其它命令会争用 SQLite。
   已加 `busy_timeout=5000` 让它等待而不是立刻报错，但建议分开目录。
2. **30 台规模未达标**：24×24 地图上 30 台车竞争激烈，7 个任务因"连续阻塞超过
   `MAX_BLOCK_TICKS=90`"被置为 `failed` 并告警。**这是显式失败，不是静默卡死。**
   个人版目标规模 10 台（`peak-10` 10/10 完成、0 死锁）；30 台是整合版的规模基线。
   若要提升，可以走"货架区扩容""增加充电桩""动态待命区"三条路，但会超出个人版范围。
3. **死锁覆盖范围有限**：只处理"等待图成环"这一类。资源饥饿、优先级反转、
   充电桩排队与任务队列之间的相互影响没有专门建模。
4. **无鉴权、无多租户、无分布式部署、无真实 AGV 通信协议**（MQTT / ROS）——
   属于整合版课程推荐技术栈范围。
5. **前端未做移动端适配与国际化**，也没有做 3D/高保真渲染。
6. **时区处理**：时间统一 UTC 存储、按 ISO 8601 字符串输出，但前端目前按浏览器本地时区显示，
   跨时区团队协作时需要再确认显示口径。
7. **AI 依赖度较高**：约 87% 的代码行由 AI 生成，剩下 13% 承载了全部逻辑正确性。
   代码审查的重点应该放在状态机与预约/死锁逻辑上，而不是样板代码。

## 12. 自我评价

**做得好的地方：**

1. **把"可验证"放在"可运行"之前**。先冻结接口契约、先写纯算法模块的单元测试、
   先给场景加定时事件机制——这些看起来都是"慢一步"的动作，但它们把
   验收从"演示一次"变成了"可重复执行"。
2. **验收阶段没有粉饰**。`peak-30` 的 7 个失败、`cycle-deadlock` 的 1 个失败，
   我都写进了报告并说明了失败规则。AC20 明确要求"不得把未运行功能标记为通过"，
   我认为这也是个人版本的信誉所在。
3. **缺陷分析做到底**。本轮记录的 21 条业务缺陷，我没有只修表面症状，
   而是逐条追问"为什么 AI 会在这里出错"，最后归纳成一条规律：
   **AI 在跨模块状态一致性上系统性薄弱**。这条规律比任何一个具体 bug 更有复用价值。

**做得不好的地方：**

1. **假覆盖差点溜过去**。`roadblock` 场景名字叫封路，实际一次封路都没发生。
   如果我只跑一遍"看起来通过了"，就会把一个没被执行的用例写成通过。
   这是本轮最惊险的一次。
2. **接口一致性核对晚了**。前后端联调是在前端全部写完之后才做的，
   中间有 snake_case / camelCase、订单缺 `lines` 等 9 处不一致。
   更好的做法是让前端子 Agent 交出"请求-响应字段对照表"再合入。
3. **性能优化投入不足**。30 台场景 9.20 ms/tick 已经足够（100 tick/秒），
   但我没有做定位分析（比如用 cProfile 找出热点），属于"够用就停"。
4. **测试的"行为断言"多于"不变量断言"**。我大量断言了"任务完成""事件出现"，
   但对"任意时刻同一格不可能有两台车"这类**不变量**缺少逐 tick 的持续检查。
   `head-to-head` 用例里的那条 SQL 检查其实只是取样，不是全量不变量。

**如果继续做下去**，我会按这个顺序：先加不变量检查（逐 tick 校验预约与占位的一致性），
再做一次 cProfile 定位 30 台场景的热点，最后把"故障注入 → 自愈"的组合场景
（故障 + 封路 + 急单同时发生）补上——因为真实仓库里最难的情况往往不是单一事件。

## 13. 运行说明

前置条件：**只需 Python 3.11 或以上**。不需要 pip install，不需要 Node，不需要 Docker。

```text
cd implementations/member-2

# 启动服务（含前端页面）
python -m wms serve --port 8099
# 浏览器打开 http://127.0.0.1:8099/
```

首次启动会自动创建 `implementations/member-2/data/wms.db` 并导入 `single-agv` 场景。

> **端口被占用**：服务启动前会探测端口。若已被别的程序监听，会直接报错退出并提示换端口，
> 不会出现"启动成功但浏览器打开的是别的程序"的静默分流。排查命令：
> `netstat -ano | findstr :8099` → `tasklist /FI "PID eq <pid>"`。

常用命令：

```text
python -m wms serve  --host 127.0.0.1 --port 8099   # 启动服务
python -m wms seed   --scenario peak-10             # 导入指定场景
python -m wms demo   --scenario peak-10 --ticks 300 # 无界面跑一段仿真
python -m wms bench  --scenario peak-30 --ticks 600 # 采集性能数据
python -m wms export-fixtures                       # 重新导出 fixtures
```

数据目录可用 `--data-dir` 或环境变量 `WMS_DATA_DIR` 覆盖。

测试与场景回归：

```text
python -m unittest discover -s tests -t tests -v     # 91 个用例
python scripts\run_scenarios.py                      # 8 个固定场景
python scripts\save_bench.py                         # 性能数据
```

演示建议：启动后在页面顶部选择 `peak-10` 场景 → 点"重置" → 点"启动/继续"并切到 8x，
可以看到 10 台车同时取货放货；再用"事件注入"注入一次 `roadblock`（格点填 `12,6`）
或 `fault`（AGV 编号填 `AGV-03`），观察地图上封路高亮、告警列表与事件流的实时变化。
