# 协作开发与工作分解

## 1. 协作原则

项目只有一个共享产品和上游主仓库。三名成员分别 fork，并在自己的 fork 中维护 `dev/member-N` 集成分支；fork 只用于并行工作，不产生个人版本或个人项目。

工作包描述的是团队需要共同完成的系统能力，不是分配给某个人的独立任务。每个 PR 由实际作者负责实现和验证，并根据变更范围邀请相关视角评审。任何成员都可以参与任一模块。

## 4. PR 切分方式

PR 按可独立验证的端到端变更切分。功能分支先合入个人集成分支，再从 fork 的 `dev/member-N` 向 `RiceXi/smart-wms-agv:main` 创建 PR。推荐范围：

- 一个接口及其契约、实现和测试。
- 一个状态机转换及其失败路径。
- 一个冲突场景及其预约、恢复和回归测试。
- 一个页面流程及其 API、WebSocket 和 Playwright 测试。
- 一个部署能力及其健康检查、指标和操作说明。

如果变更跨越多个视角，应拆分依赖顺序：契约和测试数据先提交，服务实现随后提交，前端和演示最后提交。

## 5. 协作接口

### 契约到业务

契约提案人提交 OpenAPI 或事件 schema，平台、调度和展示视角共同确认字段、状态和错误码，之后业务服务才能实现。

### 调度到仿真

调度输出路径版本、时间戳、预约和冲突原因；仿真只执行已确认计划，并回传阻塞、完成和故障事件。

### 仿真到实时展示

仿真产生带 tick 的状态事实；push 负责快照和增量；web 只渲染事实并做允许的视觉插值。

### 业务到分析

订单、任务、AGV 和告警事件进入 analytics；所有指标必须能从原始事件重算，并说明窗口与分母。

## 6. 评审轮换

- 每个 PR 至少一名非作者评审。
- 共享契约、跨服务状态或数据库迁移至少两名评审。
- 作者不能批准自己的契约变更。
- 同一成员连续承担集成协调时，应让另一名成员主持下一次里程碑评审。
- 评审意见以测试、契约和可复现结果为依据，不以个人任务边界拒绝跨模块协作。

## 7. 里程碑协作

每个里程碑开始时，团队共同确认目标、依赖和风险；开发过程中在各成员 fork 中通过功能分支提交小 PR，并合入 `dev/member-N`；退出检查时由全团队运行固定场景、记录失败项和性能数据。

未达到当前里程碑退出条件时，不创建下一阶段的新工作包。范围调整由团队共同决定，并更新总开发计划。
