# 开发分工与工作分解

## 1. 分工原则

分工按“业务闭环 + 技术所有权”划分，不按页面或文件机械切分。每名成员拥有一个端到端主方向、一个质量责任和一个集成接口。共享契约先冻结再并行开发，任何跨角色修改都要有第二个 reviewer。

## 2. 角色与交付

| 成员 | 主角色 | 主责目录 | 核心交付 | 质量责任 |
| --- | --- | --- | --- | --- |
| 成员一 RiceXi | 集成与平台负责人 | gateway、auth、wms、task、Compose、CI | WMS、任务状态机、统一入口、部署、契约合并 | 可启动、可观测、数据一致性 |
| 成员二 Zsource-Fuyi | 调度与算法负责人 | dispatch、sim、fixtures、scenario tests | 指派、时空 A*、预约、死锁、充电、tick 仿真 | 调度正确性、确定性、性能 |
| 成员三 KingSure000 | 前端与演示负责人 | web、push、analytics、e2e | Canvas 地图、WebSocket、热力、回放、指标与演示 | 实时体验、交互一致性、演示复现 |

## 3. 共享责任

| 事项 | 负责人 | 共同参与 | 完成标准 |
| --- | --- | --- | --- |
| 地图与坐标模型 | 成员二 | 成员一、成员三 | 同一样例在调度、仿真、前端完全一致 |
| 任务状态机 | 成员一 | 成员二、成员三 | 每个状态和错误码有测试 |
| AGV 状态与事件 | 成员二 | 成员一、成员三 | sim 发布、push 转发、UI 只消费 |
| API/事件契约 | 成员一 | 成员二、成员三 | schema 校验通过，兼容策略明确 |
| 演示场景 | 成员三 | 成员二、成员一 | 固定 seed、一条命令导入、脚本连续通过 |
| 里程碑集成 | 成员一 | 三人 | `main` 可构建、可启动、有失败清单 |
| 性能证据 | 成员二 | 成员一、成员三 | 调度和前端各有可重复测量方法 |

## 4. 工作包

### WP-01 仓库与契约基线

负责人：成员一。

内容：仓库结构、CI 骨架、OpenAPI、事件 envelope、错误码、分支保护、ADR 模板。

依赖：无。

验收：契约可以 lint；三个空服务或适配测试能基于 schema 生成请求；文档评审通过。

### WP-02 地图与仿真核心

负责人：成员二。

内容：地图节点、边、障碍、充电桩、拣选点、tick 常量、AGV 运动、电量、装卸、固定 seed。

依赖：WP-01 的地图字段和 tick 定义。

验收：固定脚本从起点到目标，跨边和等待行为可单测；同一 seed 输出一致。

### WP-03 WMS 主数据与订单

负责人：成员一。

内容：SKU、location、inventory、order 的 schema、服务、持久化和导入脚本。

依赖：WP-01 数据契约。

验收：库存不能为负；库位冲突被拒绝；订单可取消；API 有集成测试。

### WP-04 任务状态机与任务池

负责人：成员一，成员二参与任务重派语义。

内容：任务创建、优先级、状态流转、重派、取消、超时和对账。

依赖：WP-03 订单事件。

验收：非法流转拒绝；重复命令幂等；前端能按任务 ID 展示完整事件。

### WP-05 多 AGV 路径规划

负责人：成员二。

内容：时空 A*、等待节点、顶点预约、边预约、优先级冲突、TTL、封路重规划。

依赖：WP-02。

验收：固定冲突用例、相向穿边用例、首尾相接用例、10 台连续运行用例通过。

### WP-06 死锁与充电

负责人：成员二。

内容：等待图、环检测、受害者选择、回退、预约释放、充电阈值、充电桩排队。

依赖：WP-05。

验收：窄巷双向、三车环、低电量回充均可复现和恢复；不会无限重试。

### WP-07 实时推送与前端地图

负责人：成员三。

内容：WebSocket 协议、快照/增量、断线重连、Canvas 渲染、车辆选择、路径和告警。

依赖：WP-02、WP-05 的事件字段。

验收：30 台场景达到 20 fps；重连后 2 秒内恢复正确快照；无前端伪造状态。

### WP-08 分析服务与可观测

负责人：成员三，成员一提供指标约定。

内容：吞吐、任务耗时、利用率、瓶颈巷道 TopN、Prometheus、Grafana。

依赖：Kafka 事件和仿真时间。

验收：离线汇总与在线事件数量对账；指标有单位、时间窗口和查询示例。

### WP-09 部署与发布

负责人：成员一。

内容：Compose、kind、Ansible、镜像、启动/重置脚本、CI 制品。

依赖：WP-01 至 WP-08 的服务端口和健康检查。

验收：从空环境按文档启动；失败时给出可诊断日志；服务可重复重建。

### WP-10 验收与演示

负责人：成员三，成员二负责性能数据，成员一负责发布。

内容：固定剧本、端到端测试、压测、演示视频脚本、答辩材料。

依赖：所有 P0 工作包。

验收：连续两次完整演示通过，失败时有可切换的固定 seed 场景。

## 6. 交接规则

### 成员二向成员一交接

- 调度输入输出 schema。
- 预约键格式、TTL 语义和错误码。
- 固定场景的 seed、预期路径、冲突次数和耗时。

### 成员二向成员三交接

- AGV、路径、tick、事件和告警的字段含义。
- 快照与增量边界。
- 前端可以安全插值的字段，不能插值的字段。

### 成员一向成员二交接

- 订单和任务创建事件。
- 任务重派、取消、超时规则。
- 数据库事务边界和幂等键。

### 成员三向成员一交接

- 前端需要的查询与订阅能力。
- 指标口径和数据量。
- Playwright 失败时的复现步骤。

## 7. 评审责任

- 成员一评审契约、事务、服务边界和部署。
- 成员二评审任何影响路径、预约、tick 或状态一致性的代码。
- 成员三评审任何影响 WebSocket、Canvas、任务可视化和演示脚本的代码。
- 跨领域 PR 至少有一个非作者 reviewer；共享契约必须有两人 reviewer。
