# 项目章程

## 1. 文档目的

本文定义 SmartWMS 的目标、范围、成功标准、团队约束和决策规则。后续计划、架构与接口文档不得与本文件的核心范围冲突。

## 2. 产品定位

SmartWMS 是一个可离线演示的智能仓储与 AGV 调度系统。用户创建出库订单后，系统生成拣选任务，为任务匹配 AGV，在带障碍物的网格地图上规划时空路径，按 tick 推进仿真，并将位置、任务与告警实时显示在仓库地图上。

系统必须让业务状态、调度结果和可视化表现保持一致。镜头前的 AGV 运动不能由前端独立编造，必须来自仿真引擎发布的状态。

## 3. 核心用户场景

1. 仓库管理员维护商品、库位和库存。
2. 操作员创建出库订单并释放任务。
3. 调度器按优先级、距离和负载选择 AGV。
4. 调度器生成带时间维度的路径，并向其他 AGV 预约格点与边。
5. 仿真器按固定 tick 推进车辆，处理装卸、充电、封路和故障注入。
6. 前端展示车辆、任务、路径、拥堵、告警和指标。
7. 分析服务展示吞吐、任务耗时、AGV 利用率和瓶颈巷道。
8. 演示人员可以回放固定场景，并查看冲突与死锁处理结果。

## 4. 范围

### 4.1 必须交付

- WMS 主数据：商品、库位、库存和出库订单。
- 任务中心：任务池、优先级、指派前等待、任务状态机。
- 调度引擎：AGV 指派、时空 A*、顶点与边预约、冲突消解、死锁检测与回退、充电调度、封路重规划。
- 仿真引擎：tick 推进、AGV 运动与电量、装卸、事件注入、固定 seed、暂停、单步、回放。
- 实时可视化：2D 仓库地图、AGV 位置与轨迹、任务连线、告警、拥堵热力。
- 分析：设备与任务总览、吞吐、平均耗时、AGV 利用率、瓶颈巷道 TopN。
- 平台：统一入口、基础登录、角色权限、审计事件、OpenAPI。
- 本地部署：Docker Compose 一键启动，中间件与核心服务可重复创建。
- 测试：算法单测、服务集成测试、浏览器端到端测试和性能测试。

## 5. 优先级与保底

### P0 演示阻断

- 30 台 AGV 同时运行且无同格/穿边冲突。
- 任务能从 WMS 创建到完成，前端状态与后端一致。
- 冲突与死锁可检测并恢复。
- 20 fps 的 2D 地图体验。
- 一键启动和固定 seed 回放。

### P1 课程技术覆盖

- Kafka、Redis、Eureka、JSON-RPC、Compose、CI/CD、Prometheus、Grafana、SkyWalking。
- 任务指派 P95 小于 200 ms。
- dispatch 双实例和基础登录权限。

### P2 加分能力

- Elasticsearch 检索、HDFS/MapReduce、MinIO、Serverless、3D 场景。
- P2 功能不得挤占 P0/P1 的联调时间。若无法完整运行，保留真实实现边界和演示记录，不在界面伪造结果。

## 6. 成功标准

| 维度 | 目标 |
| --- | --- |
| AGV 规模 | 至少 30 台同时运行 |
| 前端帧率 | 测试机 2D Canvas 持续不低于 20 fps |
| 冲突 | 不出现同格冲突或相向穿边 |
| 死锁 | 连续 30 分钟运行无永久卡死 |
| 冲突消解 | 500 个随机场景中成功率不低于 95% |
| 指派延迟 | 服务端 P95 小于 200 ms |
| 仿真速度 | 1x 实时，支持 8x 加速 |
| 服务数量 | 至少 6 个容器化微服务，计划交付 8 个 |
| 可观测 | Grafana 有吞吐、冲突、死锁、利用率；SkyWalking 可看跨服务链路 |
| 可重复性 | 固定 seed 重跑得到相同任务序列与关键事件 |

## 7. 非目标

- 不连接真实 AGV、PLC、WCS 或仓储硬件。
- 不实现真实支付、邮件、短信和外部地图。
- 不在第一阶段建设多租户、多仓或复杂审批。
- 不把 3D 作为主线；只有 P0/P1 完成后才进入。
- 不以高保真物理碰撞替代离散网格仿真。

## 8. 团队约束

- 项目只有一个共享产品；fork 和 `dev/member-N` 只隔离并行工作，不产生个人版本。
- 三名成员分别维护个人 fork 和集成分支，最终通过 PR 合入上游 `main`。
- 三名成员围绕同一套架构、契约和验收目标协作；成员名称仅表示主要评审视角。
- 任何成员都可以修改共享代码，项目不设置独占个人目录。
- 共享契约冻结后，只能通过 ADR 和至少两人评审修改。
- 每个里程碑通过个人 fork 的集成分支和跨 fork PR 集成到上游 `main`。
- 任何成员发现契约歧义时，先记录 issue，不在单个服务内自行改变字段语义。

## 9. 决策规则

1. 先保 P0，再补 P1，最后尝试 P2。
2. 先证明调度正确，再优化视觉表现。
3. 先使用固定场景复现，再扩展随机压测。
4. 能用简单确定性算法证明正确的功能，不引入复杂框架。
5. 任何性能结论必须附测试环境、数据规模和测量方法。
6. 发生冲突时，以数据契约、测试结果和可复现证据为准。
